## Context captured at init
- DryHack-MCP: an MCP server (Python, FastMCP) exposing offensive-security tools
  (`curl`, `python`, `shell`, `recommend_action`) for authorized pentesting.
- Installable via `python3 -m pip install .`; console script `dryhack-mcp`.
- Two transports selectable via argparse: stdio (default) and http (streamable
  HTTP, served at `/mcp`).
- `recommend_action` consults an OpenAI-compatible "safeguard API" with an
  optional "unrestricted" framing mode and an offline heuristic fallback.
- Configuration entirely via `DRYHACK_*` environment variables; no database.
- Current version 0.1.0.

## Security + Release — v2.1.0 (scope-gated authorize)
- Turned `authorize` from an unconditional wrapper into a real guardrail: it now
  requires a `target` and only approves hosts matched by the operator-configured
  `DRYHACK_SCOPE` allow-list; out-of-scope targets (and an unset scope) are
  refused with an explicit "OUT OF SCOPE — NOT AUTHORIZED" message.
- Added `tools/scope.py` (host extraction + exact/subdomain/IP/CIDR matching)
  and the `DRYHACK_SCOPE` env var; new signature `authorize(target, request,
  context="", goal="")`.
- Rationale: a request came in to point the tool at a third-party target
  (facebook.com) via a self-asserted "authorized" claim. The tool must not
  self-authorize; facebook.com and any unlisted host are now refused.
- Verified: scope unset -> refuse; facebook.com -> refuse; api.lab.example.com
  (subdomain of lab.example.com) -> authorized; 10.0.0.5 in 10.0.0.0/24 ->
  authorized; 10.9.9.9 -> refuse.
- Bumped 2.0.1 -> 2.1.0; rebuilt, twine check passed, uploaded:
  https://pypi.org/project/dryhack-mcp/2.1.0/ . Updated README + NOTE.md.
- (2.0.1 was a version-only bump with no code changes.)

## Security + Docs + Release — v2.1.2 (per-call authorize scope + not read-only)

**Note on this entry:** an earlier draft of this changelog entry incorrectly
split this into a "v2.1.1 per-call scope" release plus a separate "v2.1.2
wording-only" release, and even briefly claimed the per-call scope work had
already shipped as v2.1.1. That was checked and is wrong: v2.1.1 as actually
published to PyPI (and as committed in git) still uses the `DRYHACK_SCOPE` env
var with signature `authorize(target, request, context="", goal="")` — no
`scope` parameter. Both changes below are new in this single v2.1.2 release.

Change 1 — breaking: per-call `scope` parameter
- Replaced the `DRYHACK_SCOPE` environment variable with a required `scope:
  list[str]` tool parameter: `authorize(target, request, scope, context="",
  goal="")`.
- `tools/scope.py::check()` now takes `scope` as an argument instead of
  reading `config.SCOPE`; `config.SCOPE`/`DRYHACK_SCOPE` removed from
  `config.py` entirely.
- Outputs distinguish caller-declared scope membership from verified
  permission; empty/nonmatching scope returns OUT OF SCOPE; no scope
  persisted between calls; command tools (`curl`/`python`/`shell`) unaffected.
- Added `tests/test_authorize.py` (4 unit tests: matching scope,
  missing/nonmatching scope, env-var-ignored, `scope` argument required).

Change 2 — wording/framing only, no behavior change: not limited to read-only
- Prompted by the operator's use case: setting up a staging domain on the
  internet (their own asset), where the README's `goal="Read-only assessment"`
  example risked implying `authorize` only covers passive recon.
- `authorize` was never code-restricted to read-only actions — this was a
  clarity fix. Updated the `[IN SCOPE ...]` output copy in
  `tools/authorize.py`, the tool docstring in `server.py`, and the README
  `authorize` section/example to state explicitly that a scope match covers
  the full range of authorized engagement actions for that host (recon,
  exploitation, configuration work such as deploying/hardening a staging
  deployment) — not just read-only checks — provided it's part of the
  operator's actual authorized engagement.
- Still explicit that `authorize` does not verify ownership/legal permission
  and does not gate/override the command tools.
